# FF3 V17: native modes compared against coverage

The supplied V15 report's last recorded automatic request is a Dime with 3.494 seconds of flight and power 79. It records ten automatic API requests, no ambiguous requests and no fatal exception. Its explicit `NATIVE_MODE_OWNERSHIP|YUNA; NO_SELECTEDTYPE_OR_AUTO_MODE_WRITES` confirms that the active recovery release was still using Yuna's movement-based automatic mode. The user reports the last throw went into prevent coverage and that deep burns are being missed. The report contains no throw-time player positions or trajectory vector: it cannot establish that defender's location, whether a safer alternate mode existed, or exactly which check admitted the throw. API acceptance does not establish a catch or server acceptance.

Code inspection supports three relevant weaknesses. Native automatic mode has no defender input; V15 evaluates only its one resulting mode. V15 projects defenders along their current velocity with small uncertainty, so a stationary prevent defender's ability to pursue a slow lob is underestimated. Its separate arrival-separation tax grows with flight time, which can reject a trailing-DB burn without considering the actual running race. Camera visibility also excluded otherwise eligible teammates. Rotating receiver selection and same-mode hold resets could delay releases. These are supported implementation weaknesses, not a reconstructed explanation of every live interception.

## What changed

Pelican compares **receiver + native Bullet/Fit/Dime/Jump output**. It retains the qualified Yuna target lock, actual final native velocity/time, native numerical settings and leads, SmartPass and exact AntiOOB clamp. It does not add new launch-angle presets, arbitrary height offsets, camera animations or anti-cheat hooks. Native Jump is not a newly calibrated Bullet-speed high-jump throw. The inspected source's native Bullet/Fit use fixed power 95 and a lower ballistic branch; Dime/Jump retain the user's Angle/Power configuration. Distance alone does not impose a mode.

The V16 setup failure is addressed at the integration boundary. V17 does **not** ask the user to leave native automatic mode disabled. Each own calculation temporarily sets `AutoThrowType.Enabled=false` and `SelectedType` to the candidate, because the nested native solver independently reads that setting. It restores both immediately after the synchronous calculation, including exceptions. The native calculator runs through a protected coroutine resume: an unexpected yield is cancelled and stops Pelican with settings already restored. Stop/replacement also restores an in-progress scope. Conflicting external edits are preserved and stop automatic control. Before setup, between calculations and after shutdown, normal Yuna automatic/manual mode settings remain available. Native UI/dropdown values between calculations describe restored Yuna settings; Pelican's recorded throw mode and final vector describe its actual request.

For each native path, the controller analytically finds the times the ball enters the inherited defender vertical-reach interval. At those times it checks horizontal distance against a defender's optimistic running reach: maximum of current horizontal velocity, observed horizontal speed and current Humanoid WalkSpeed, multiplied by elapsed flight time, plus the inherited horizontal reach estimate. This permits an immediate change of direction, favoring the defender. A stationary prevent defender can pursue a lob; a trailing defender must actually cover the distance before arrival. Endpoint clearance uses this same running race instead of adding the old flight-growing separation tax. Vertical reach estimates, the 4.5-stud horizontal allowance and release-clearance margins are inherited **uncalibrated policy assumptions**, not verified FF3 interception hitboxes. Conservative pursuit can still reject a catchable window; acceleration, reaction, dive/mag capabilities and server catches are not established.

A release-qualified option outranks a merely selectable one. Extra safety clearance saturates for ranking, so a floating pass cannot win simply by accumulating surplus empty space after a direct pass is already safe. Shorter flight and smaller correction from native predicted receiver motion improve ranking among safe candidates. No suitable native output means hold the ball. Actual arrival must agree horizontally with the native aimpoint after its exact AntiOOB clamp, preventing fallback/later-crossing outputs from silently overshooting. A necessary optimistic receiver running/lead bound rejects clearly unreachable arrivals; it does not prove the receiver will react, jump or catch.

The planner considers an incumbent and rotating challengers, with per-receiver safe history rather than a timer discarded on each challenger or mode change. Off-camera teammates remain eligible. Current team, alive, blacklist, continuous observed movement, verified LOS, six-yard downfield depth and field bounds still apply. No AFK or inside-LOS fallback was added. Unsampled defenders block release; a newly joined teammate does not reset all existing receivers. Minimum play development is two seconds, with 2/3/4-second pace controls; continuous safe hold is 0.24 seconds. These are deliberate responsiveness policies, not catch calibration.

Work is bounded to six candidate solves, one winner refresh and one immediate release validation per 0.12-second controller tick. Candidate work has an 8 ms budget, which cannot preempt a non-yielding native call. Four modes rotate fairly when work is deferred. Cache age is at most 0.36 seconds; current observations recheck cached candidates and a fresh solve is mandatory before release. Native numerical configuration/lead edits invalidate cached opportunities. Receiver menu pauses solving/release, maintains motion observation and clears safe history on closure. One attempt per possession, manual animation ownership and no ambiguous automatic retries remain unchanged.
